# P4.4.12.1 — Base de démonstration showcase

## But

Branche `p4.4.12.1-showcase-demo`, créée depuis
`c3a9409 Reorganize personal space UX`, dépôt initialement propre.

La showcase est une base locale reproductible pour démonstration, recette UX
et responsive. Elle complète la démo propre sans la remplacer :
`reset-demo.sh`, `VerifyDemo`, le référentiel `budokan.sql` et `run-dev.sh`
restent inchangés. La démo standard conserve trois comptes bureau, une saison,
zéro essai, zéro adhésion et zéro membre.

## Utilisation

```bash
./scripts/reset-showcase-demo.sh
DATABASE_PATH=data/clubcore_showcase_demo.db ./scripts/run-dev.sh
```

Le reset affiche le chemin, le mot de passe, les comptes, leurs scénarios et
la commande de lancement. Le lancement conserve les dossiers showcase ;
seule la préparation additive du référentiel Budokan existant est exécutée.

Options locales : `DATABASE_PATH` pour une autre base explicitement `_demo`,
`CLUBCORE_DEMO_PASSWORD` pour un autre mot de passe de 12 à 72 octets.
Le script utilise le même défaut que la démo standard.

Vérification explicite de la base immédiatement après reset :

```bash
DATABASE_PATH=data/clubcore_showcase_demo.db \
CLUBCORE_DEMO_PASSWORD=mon-mot-de-passe-de-test \
go run ./cmd/clubctl verify-showcase-demo --confirm-demo
```

Cette vérification contrôle le scénario initial exact. Après des modifications
manuelles de dossiers, relancer le reset pour retrouver ce scénario.
Les bases SQLite et captures sont locales et exclues de Git.

## Architecture et fichiers

- `internal/demodata/showcase.go` : `PrepareShowcase` et `VerifyShowcase`.
  Seed single-use dans une transaction SQLite immédiate ; prérequis stricts
  Budokan + bureau + absence de données métier ; vérification avant commit.
  Échec ou nouvelle exécution : refus/rollback, aucun upsert silencieux.
- Références résolues par noms de saison, activité, groupe, type, code de
  consentement, username et identités retournées par les insertions.
  Aucun ID numérique fixé. Dates des nouveaux dossiers fixes ; hashes bcrypt
  produits séparément par `auth.HashPassword`, avec sels distincts.
- `internal/demodata/reset_guard.go` : contrôle préalable de suppression,
  construit sur `CheckDemoPath`.
- `cmd/clubctl/main.go` : commandes `prepare-showcase-demo`,
  `verify-showcase-demo`, `check-demo-reset-path`, toutes à confirmation
  explicite et contrôle avant ouverture de base.
- `scripts/reset-showcase-demo.sh` : validation, build, contrôle Go, suppression
  ciblée base/sidecars, migrations existantes, Budokan, bureau, showcase,
  vérification et instructions.
- Tests : `internal/demodata/showcase_test.go`,
  `scripts/reset_showcase_demo_test.go`,
  `internal/application/showcase_demo_integration_test.go`,
  `cmd/clubctl/main_test.go`.

Aucune migration, modification de schéma ou SQL/sqlc métier. Aucun changement
de permissions, de règle métier ou de template/CSS. Aucun document ou PDF créé.

## Sécurité

Refus des noms non `_demo`, chemins ambigus, composantes `..`, symlinks de la
base ou de ses dossiers parents, sidecars `-wal`/`-shm` symboliques ou non
réguliers. Validation du mot de passe en octets avant suppression.
Le build et le contrôle Go doivent réussir avant tout effacement.
Une base réelle voisine et ses sidecars ne sont jamais ciblés.

Chaque compte est actif, activé et authentifiable avec son propre hash bcrypt.
Les quatre enfants n’ont pas de compte interactif ajouté ; leur accès passe
par les relations et droits familiaux existants de Claire.
Les contraintes et triggers SQLite restent activés.
