# Club Core — P4.4 — Migration PostgreSQL → SQLite

Date : 30 septembre 2026. Référence : `p4.3-recipe-feedback`, commit `1a6e7dd`. Branche : `p4.4-sqlite-migration`.

## 1. Résumé

SQLite devient l’unique moteur de données. Le serveur, le CLI, sqlc, les migrations, les services transactionnels, les tests et la démonstration Budokan utilisent désormais un fichier SQLite. Les parcours, formulaires, règles d’adhésion et d’essai, permissions, consentements et règles concernant les mineurs sont conservés.

L’audit a précédé les modifications : dépendances Go et outils, configuration, documentation, 35 migrations, requêtes sqlc et SQL écrit dans les services/tests, types générés, transactions et verrous. Le schéma final réellement produit par les anciennes migrations a également été inspecté pour conserver les clés, contraintes, index et protections d’historique. La base PostgreSQL de démonstration existante n’a pas été convertie ni réinitialisée.

Le plan retenu était : baseline du schéma final, driver et types SQLite, génération sqlc, adaptation des services et des verrous, bases temporaires de test, outillage local et seed, puis contrôles complets et fonctionnels. Aucun backend alternatif n’a été conservé.

## 2. Architecture

### Driver et connexion

Driver : `modernc.org/sqlite v1.60.1`, compatible `database/sql`, sans CGO. Cette version convient au Go 1.26.5 du dépôt et fournit SQLite 3.53.4 sur Linux amd64, ARM et ARM64. Les builds Linux ARMv7 et ARM64 ont été vérifiés avec `CGO_ENABLED=0`. Le choix évite une chaîne de compilation C sur les petites installations. Référence : [documentation modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite).

`database.New(ctx, path)` ouvre un `*sql.DB`. `DATABASE_PATH` vaut par défaut `data/clubcore.db`. Le chemin est transformé en chemin absolu et encodé comme URI de fichier ; le dossier est créé en mode 0700 et un nouveau fichier en mode 0600. Les erreurs de création/ouverture indiquent le chemin concerné. Le serveur et le CLI ferment la DB ; le serveur attend aussi l’arrêt du worker et termine les requêtes HTTP en cours.

Le pool comporte au maximum huit connexions ouvertes et huit connexions conservées. Les réglages sont transmis par le DSN du driver, donc appliqués à **chaque connexion physique**, y compris celles créées après l’ouverture initiale :

| Réglage | Valeur | But |
| --- | --- | --- |
| `foreign_keys` | `1` | Application effective des relations |
| `busy_timeout` | `10000` ms | Attente d’un écrivain concurrent |
| `journal_mode` | `WAL` | Lectures possibles pendant une écriture |
| `synchronous` | `FULL` | Durabilité des commits |
| `_txlock` du driver | `immediate` | Réserver l’écriture avant lecture/validation |

Le test des huit connexions réserve simultanément chaque connexion, vérifie ses PRAGMA et tente une insertion violant une foreign key. La lecture WAL pendant une transaction d’écriture est testée via un second handle. Référence : [PRAGMA SQLite](https://sqlite.org/pragma.html).

### Types et fonctions

Les types nullable standards sont `sql.NullString`, `sql.NullInt32`, `sql.NullInt16`, `sql.NullInt64` et `sql.NullBool`. Les IDs métier restent des `int32` en Go ; les comptes nécessitant un `int64` gardent ce type explicitement.

`dbtypes.Date`, `Time` et `Timestamp` implémentent `sql.Scanner` et `driver.Valuer`. Les dates civiles utilisent `YYYY-MM-DD`, les heures gardent les minutes et, si présentes, les secondes/fractions, et les timestamps sont normalisés en UTC avec précision milliseconde. Les calculs métier conservent leur fuseau, notamment `Europe/Paris`, et leur logique calendaire. Les dates invalides et les valeurs booléennes autres que 0/1 sont refusées par les contraintes.

Quelques fonctions déterministes Go sont enregistrées sur le driver : validation des emails/URL/types de liens, normalisation des chiffres du téléphone et minuscules Unicode. Elles conservent les contraintes et la recherche existantes sans installer d’extension SQLite.

## 3. PostgreSQL supprimé

Retrait de `github.com/jackc/pgx/v5`, `pgxpool`, des types pgx et des dépendances Testcontainers, dont son module PostgreSQL. Les dépendances Docker/Moby devenues inutiles ont également disparu après `go mod tidy`.

`sqlc.yaml` utilise `engine: sqlite` et `sql_package: database/sql`. Les 26 fichiers Go générés ont été régénérés depuis les sources SQL, sans correction manuelle durable. Les tests utilisent chacun leur propre fichier dans `t.TempDir()` et passent sans Docker.

`DATABASE_URL`, les DSN PostgreSQL, le conteneur de base, le port 5433 et le CLI Goose requis pour l’installation ont été retirés de la configuration et du démarrage. Goose reste la bibliothèque de migrations SQLite embarquées. Le serveur et le CLI appliquent ces migrations automatiquement ; `clubctl migrate` permet aussi de le faire explicitement.

Le script de développement fonctionne avec Go seul. Le transport email y est désactivé par défaut ; Mailpit reste une option documentée, indépendante de la base. L’outil de campagne multi-utilisateur conserve uniquement son éventuelle capture SMTP Docker et utilise une base SQLite locale isolée. Les rapports historiques restent inchangés comme archives des jalons précédents.

## 4. Adaptations SQL importantes

| Construction précédente | Adaptation SQLite |
| --- | --- |
| `ARRAY(...)`, `array_agg`, `integer[]`, `text[]` | Projections JSON SQLite ordonnées avec `json_group_array`, lues comme slices Go ; liste éditoriale de l’organisation stockée en JSON validé |
| `ANY(...)` | `IN (sqlc.slice(...))` pour les listes sqlc ; `json_each` pour quelques listes de paramètres dans le SQL Go ; valeurs fixes avec `IN (...)` |
| `INTERVAL` et arithmétique de dates | `date(...)` pour les dates civiles et `strftime` pour les délais en secondes ; calculs Go calendaires existants conservés |
| Soustraction de 18 ans | `date(trial_date,'-18 years','floor')` ; le 29 février retombe au 28 février dans une année non bissextile, sans approximation en jours |
| `to_char(...,'HH24:MI')` | `substr(...,1,5)` pour conserver exactement `HH:MM` |
| `regexp_replace` du téléphone | Fonction Go déterministe `normalize_phone`, utilisable sur chaque connexion ; même conservation des chiffres ASCII |
| `LEFT JOIN LATERAL` | Jointures par ID choisi dans une sous-requête corrélée, avec mêmes critères et ordres de sélection |
| `NULLS LAST` | Conservé : pris en charge par la version SQLite embarquée ; les ordres administratifs sont testés |
| Casts `::date`, `::text`, `::boolean`, `::integer` | Dates canonisées en Go ; `CAST` SQLite explicites pour textes, booléens et nombres là où nécessaires à sqlc |
| `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` | Lectures dans une transaction `BEGIN IMMEDIATE`, qui protège validation et écriture contre tout autre écrivain |
| `FOR UPDATE SKIP LOCKED` de l’outbox | Réclamation atomique par `UPDATE` sur un ID éligible ordonné, puis `RETURNING` ; bail et génération conservés |
| `NOW()`, `clock_timestamp()`, `TIMESTAMPTZ` | Texte UTC via `strftime('%Y-%m-%d %H:%M:%f','now')` et type Go `Timestamp` |
| Identity PostgreSQL | `INTEGER PRIMARY KEY AUTOINCREMENT`, IDs non réutilisés |
| Contraintes et fonctions PL/pgSQL | Contraintes SQLite, index partiels et triggers `RAISE(ABORT,...)` |

La recherche dans l’annuaire reste une recherche littérale avec `instr`, y compris pour `%` et `_`. Les recherches auparavant fondées sur `ILIKE` utilisent les minuscules Unicode avant `LIKE`. Les agrégats gardent les listes vides et l’ordre attendu ; les `NULL` optionnels restent distincts des valeurs présentes.

Les paramètres SQL Go sont numérotés `?1`, `?2`, etc. Les paramètres sqlc sont nommés. Certaines comparaisons `BETWEEN` avec paramètres et expressions de tri ont été reformulées en comparaisons simples/projections pour obtenir une génération correcte avec sqlc SQLite. Les casts utilisés pour typer les projections JSON indiquent une affinité texte SQLite, pas un type array PostgreSQL.

Les tests ont détecté les nombres JSON à convertir en chaînes dans les formulaires de configuration et les dates Go à convertir en dates civiles avant comparaison. Un test supplémentaire vérifie que la fin de saison ou de créneau **exactement le premier jour réservable** reste inclusive et permet une réservation.

## 5. Transactions

Toutes les transactions applicatives utilisent la configuration `immediate` du driver. Le verrou d’écriture est obtenu au début, avant la lecture qui décide si l’opération est autorisée. Un second écrivain attend puis relit l’état commité. Il n’y a donc pas de conversion tardive d’un snapshot de lecture en écriture concurrente.

| Invariant auparavant protégé par un verrou PostgreSQL | Protection actuelle et validations |
| --- | --- |
| Quota d’essais, changement de résultat ou de saison, calendrier et configuration actifs | Transaction IMMEDIATE autour des contrôles et modifications ; test quota avec deux handles SQLite, créations/statuts/transferts concurrents |
| Une adhésion par personne/saison, une seule approbation et préparation de compte | Transaction IMMEDIATE, contraintes uniques et rollback ; tests d’approbations/activations concurrentes |
| Affectation de groupe et fermeture d’une affectation | Validation et écriture atomiques, index unique partiel `left_at IS NULL` ; tests de courses administratives |
| Consentements présentés, identité et responsable éligibles | Snapshot protégé pendant l’écriture, exigences et historique immuables ; tests des permissions et des décisions de consentement |
| Relation guardian, accès, révocation et préparation d’activation | Transaction IMMEDIATE et triggers interdisant la suppression/changement d’une relation portant un accès actif ; tests guardian concurrents |
| Configuration initiale unique et maintien du dernier gestionnaire d’accès | Transaction IMMEDIATE remplace le verrou de ligne/setup et le verrou consultatif des rôles ; tests de créations/retraits concurrents |
| Idempotence d’inscription, résolution, confirmation guardian et finalisation | Transaction IMMEDIATE, clé de requête unique, états finaux immuables ; tests de soumissions et finalisations concurrentes |
| Budget d’emails par destinataire et seed vide unique | Contrôle et insertion dans la même transaction d’écriture ; tests de quota familial et de seeds concurrents |

Les savepoints de création d’adhésion utilisent explicitement `SAVEPOINT`, `ROLLBACK TO` et `RELEASE`. Ils conservent une preuve d’identité validée lorsque la création métier échoue, comme auparavant.

L’exclusion entre SMTP et décisions d’identité demande une protection hors transaction. Un verrou système de fichier par soumission, dans `<base>.locks/`, remplace le verrou consultatif de session. Le worker et les services de décision l’acquièrent **avant** d’ouvrir une transaction IMMEDIATE. SMTP ne conserve aucun verrou SQLite ; les tests vérifient qu’une transaction d’écriture reste possible pendant un envoi bloqué. Le verrou de fichier fonctionne entre handles/processus locaux et est libéré par le système en cas de fermeture ou de crash. Les fichiers eux-mêmes ne portent aucune donnée métier ni secret.

La réclamation de l’outbox reste atomique ; le numéro de bail exclut les fins de traitement obsolètes. Le verrou de livraison interdit aussi un deuxième envoi tant qu’un ancien expéditeur est encore actif. La résolution annule les travaux ouverts via un trigger. Les tests couvrent deux workers, reprises après expiration, décisions administratives concurrentes et envois en attente.

Le test d’échec de commit utilise une foreign key réellement différée : l’écriture réussit, le commit échoue, toute la transaction est annulée et aucun email d’activation n’est livré.

## 6. Migrations

Les 35 migrations pré-production ont été consolidées en `0001_sqlite_baseline.sql`, représentant leur schéma final. Les étapes historiques de changements de contraintes, fonctions PL/pgSQL et backfills n’ont pas à être rejouées dans une installation neuve. Il n’existe aucune migration PostgreSQL parallèle ni outil de conversion de bases existantes.

La comparaison du schéma final confirme la conservation des 38 tables hors métadonnées Goose et des 34 index explicitement créés. Les foreign keys, contraintes uniques et CHECK, index ordinaires et index partiels ont été conservés ; une foreign key technique différée a été ajoutée pour l’activité obligatoire. Les triggers préservent les définitions de consentement, les preuves et décisions, les candidats d’identité, les intentions d’inscription, les confirmations enfant et l’historique des accès guardian. SQLite ne propose pas `TRUNCATE` ; les suppressions de lignes des historiques restent interdites.

L’obligation d’au moins une activité par demande, précédemment vérifiée par un trigger différé PostgreSQL, utilise une colonne technique immuable `required_activity_id` et une foreign key composite **DEFERRABLE INITIALLY DEFERRED** vers les activités de cette demande. L’application choisit une activité déjà validée et insère l’ensemble dans la même transaction. Une demande sans activité ne peut pas être commitée ; un test le vérifie explicitement.

Les quatre rôles initiaux et la ligne singleton de setup sont conservés. La baseline n’ajoute aucun utilisateur ni club de démonstration automatiquement. Son `Down` est atomique et refuse une base contenant des données métier ; le roundtrip sur base vide et les refus de rollback destructeur sont testés. Les tests de migrations historiques ont été adaptés à cette baseline ; les backfills d’anciennes bases PostgreSQL ne font plus partie du contrat.

Les migrations sont embarquées avec `go:embed` et appliquées via le provider Goose SQLite. Toute migration future partira de cette version 1.

## 8. Limites connues

SQLite autorise un seul écrivain à la fois. Le délai d’attente de 10 secondes et les transactions courtes conviennent au bureau d’une petite ou moyenne association ; ils ne constituent pas une garantie pour des écritures artificiellement bloquées au-delà de ce délai. La stratégie IMMEDIATE privilégie la cohérence et sérialise aussi les transactions de services qui prennent un snapshot avant validation.

WAL et les verrous système de livraison supposent une base sur un système de fichiers local, pas un fichier partagé entre serveurs via NFS/SMB. Une instance sur NAS doit utiliser son stockage local. Pour une copie portable, arrêter l’application puis copier la base et les fichiers ; conserver également un WAL/SHM encore présent. Les verrous de livraison peuvent être recréés au prochain démarrage.

Les timestamps persistés ont une précision milliseconde ; les lectures chronologiques qui départagent des événements gardent leur ID comme critère supplémentaire. Les valeurs date/heure infinies de PostgreSQL ne sont pas représentées ; les entrées métier exigent des dates civiles finies. Les fonctions de validation Go doivent être enregistrées pour écrire directement les champs concernés depuis un outil SQLite externe ; utiliser le CLI/application conserve ces contraintes automatiquement.

Les builds ARM ont été compilés et inspectés, sans exécution sur un appareil Raspberry Pi physique. Aucun transfert des anciennes données PostgreSQL n’est inclus, conformément à la décision pré-production.

## 9. Suite recommandée

Le projet est suffisamment stable pour reprendre la chaîne d’inscription et l’utiliser comme recette réelle de SQLite : schéma neuf, seed, parcours et invariants concurrents sont validés. Conserver SQLite comme moteur unique et ajouter les migrations futures à partir de la baseline actuelle. Le transfert hors ligne de la base et des fichiers répond déjà au besoin immédiat de portabilité ; aucun chantier général d’export/import n’a été ajouté.
