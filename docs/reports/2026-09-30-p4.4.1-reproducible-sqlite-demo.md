## 6. Fonctionnement de reset-demo.sh

Depuis le dépôt :

```bash
./scripts/reset-demo.sh
./scripts/run-dev.sh
```

Le reset se place à la racine du dépôt, choisit `DATABASE_PATH` ou `data/clubcore_demo.db`, valide le nom et les fichiers cibles ainsi que la longueur du mot de passe, normalise le chemin avec `realpath -m`, puis compile un exécutable temporaire `clubctl` avant tout effacement.

Il supprime uniquement le fichier ciblé et ses deux sidecars `-wal` et `-shm`, sans glob ni suppression récursive. Il enchaîne `migrate`, `seed-budokan --confirm-empty-demo`, `prepare-demo-office --confirm-demo`, puis `verify-demo --confirm-demo`. Une erreur arrête le script ; le résumé de succès n’est imprimé qu’après toutes les vérifications. L’exécutable temporaire est supprimé par un trap.

Le résumé donne le chemin absolu, Budokan, les nombres de références, les trois identifiants/rôles, le mot de passe local et les compteurs métier à zéro. Il rappelle `./scripts/run-dev.sh`.

## 7. Garde-fous _demo

Le nom du fichier doit finir par `_demo`, éventuellement suivi de `.db`, `.sqlite` ou `.sqlite3`. Les chemins de type URI, les chemins terminés par `/`, les retours à la ligne, les liens symboliques (y compris pendants), les répertoires et les fichiers non réguliers sont refusés. Le contrôle des liens/fichiers porte aussi sur WAL et SHM avant suppression.

Les commandes de démonstration vérifient `DATABASE_PATH` et le flag explicite avant d’ouvrir ou migrer la base. Les fonctions Go vérifient à nouveau la base réellement ouverte via `PRAGMA database_list` dans leur transaction. Les comptes exigent un référentiel Budokan conforme et aucun dossier métier ni identité préexistante.

La protection repose sur une désignation explicite de démonstration. Elle ne peut pas reconnaître une base réelle délibérément copiée ou renommée `_demo` : ce mécanisme ne doit jamais être utilisé sur une telle base. L’effacement exige l’arrêt préalable du serveur ; le script ne pilote pas automatiquement ses processus.

## 8. Mot de passe par défaut et surcharge

La valeur est définie explicitement dans `scripts/reset-demo.sh` :

```bash
CLUBCORE_DEMO_PASSWORD="${CLUBCORE_DEMO_PASSWORD:-mon-mot-de-passe-de-test}"
```

Elle est exportée pour les deux commandes Go, sans passage par un argument CLI. Surcharge :

```bash
CLUBCORE_DEMO_PASSWORD='autre-mot-de-passe-demo' ./scripts/reset-demo.sh
```

La politique existante de 12 à 72 octets est appliquée. Une valeur invalide est refusée avant l’effacement. L’affichage du mot de passe en fin de reset concerne uniquement ces comptes synthétiques locaux. Aucun mot de passe en clair n’est écrit dans SQLite.

## 9. Création et hash des comptes

`demodata.PrepareDemoOffice` ouvre une transaction SQLite IMMEDIATE selon la configuration normale du driver. Elle vérifie le fichier, l’absence de personnes/utilisateurs/rôles attribués, l’absence de configuration initiale déjà engagée, les références et toutes les tables non référentielles.

Pour chaque compte, elle appelle `auth.HashPassword` avec bcrypt et son coût existant, en générant un sel indépendant. Elle crée ensuite une Person, un User actif avec `activated_at`, et une association normale `user_roles`. L’email synthétique est `<identifiant>@clubcore.invalid`. Un rôle absent ou une erreur d’écriture annule les trois comptes et l’état d’installation.

Le bootstrap vérifie les trois identités, leurs seuls rôles et leur authentification avant commit. Le comportement choisi à la réexécution est un **refus explicite** (`ErrOfficeNotEmpty`), sans changer les mots de passe ni dupliquer les personnes. Pour repartir, utiliser le reset complet.

## 11. Pourquoi les rôles n’ont pas de mot de passe

Un rôle décrit des permissions. Une identité User est authentifiée par son `password_hash`, puis ses rôles sont lus par `user_roles`. Le mot de passe appartient donc à un User ; plusieurs utilisateurs peuvent partager un rôle tout en ayant leurs propres identifiants et mots de passe. Aucune colonne ni notion de mot de passe de rôle ajoutée.

## 12. Séparation entre setup réel et bootstrap démo

Le mécanisme `/setup`, ses secrets, validations et règles de création du premier président sont inchangés. Le bootstrap démo est un outil CLI de développement distinct, sans appel à `/setup`. Après création du président démo, la transaction marque l’installation initialisée, référence ce User dans `first_admin_user_id` et ne laisse aucun secret de setup. La démo ne peut donc pas être reprise par le parcours initial d’installation.

## 13. Interaction reset / run-dev

`reset-demo.sh` est la commande volontairement destructive pour la démo. `run-dev.sh` est conservé sans modification : migration, seed sur base vide ou upgrade Budokan existant, puis serveur. Il n’efface jamais la base et ne recrée pas les comptes du bureau.

Un lancement de `run-dev.sh` seul sur un fichier neuf conserve son ancien comportement, avec un seed de références uniquement. Pour obtenir les trois comptes prêts à la recette, exécuter d’abord le reset. Pour un autre chemin démo, fournir le même `DATABASE_PATH` aux deux scripts.

## 14. Upgrade d’une ancienne démo

L’upgrade conserve les personnes, essais, adhésions et relations existantes. L’ancien transfert du créneau technique du lundi vers le groupe public JJB reste idempotent : le créneau historique est conservé et désactivé, sans changer les références des essais passés.

L’ancienne activité `Préparation physique`, si présente, est désormais désactivée au lieu d’être supprimée. Ses FK, groupes, créneaux et historiques restent en base. Une ancienne démo peut donc garder 3 lignes d’activités, dont 2 actives. Un reset neuf produit directement 2 lignes.

L’upgrade complète les trois prix seulement lorsque `amount_cents IS NULL`. Il conserve les montants existants, même zéro, leur devise et leur note. Une note déjà renseignée est aussi préservée lors du complément d’un montant absent. Aucun nettoyage destructif ni remise à zéro par l’upgrade.

## 20. Limites et futur chantier Trésorerie

Le reset est local et destructif, destiné exclusivement aux fichiers explicitement démo. Il requiert Bash, Go et les utilitaires GNU usuels. Arrêter le serveur avant de l’utiliser. Les étapes complètes du reset ne forment pas une transaction unique : un échec après suppression laisse une démo incomplète, sans résumé de succès ; relancer la commande permet de repartir. Le bootstrap des comptes, lui, est transactionnel.

La saison 2026/2027 est fixe ; après son terme, le fonctionnement normal des projections publiques ne sélectionnera plus ce planning comme courant. Le texte de consentement et les tarifs restent fictifs. Les hashes et timestamps changent à chaque reset ; les identités, références et possibilités de connexion sont reproductibles.

Le trésorier garde la politique actuelle, vide de permissions administratives. Paiements, crédits, soldes, reçus, indicateurs payé/non payé et nouvelles permissions financières sont volontairement laissés au futur chantier Trésorerie.
